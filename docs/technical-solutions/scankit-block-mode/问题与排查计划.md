# 五、优先检查是否存在“按输入大小增长”的临时内存


这种情况需要重点确认。

# 七、检查 Scanner 是否每次 Scan 都重新构造执行状态

例如：

```go
func (s *Scanner) scanInto(data []byte, matches []Match) ([]Match, error) {
    states := make(...)
    ...
}
```

如果 `states`、`nodes`、`queue`、`visited` 等对象每次 Scan 都重新创建，需要判断：

1. 是否真的需要
2. 是否可以复用
3. 是否可以使用固定容量
4. 是否可以使用 stack / small buffer
5. 是否可以通过 Scanner 生命周期持有 scratch buffer

例如：

```text
Scanner
├── immutable compiled rules
├── reusable scratch
└── Scan
```

而不是：

```text
Scan
├── allocate scratch
├── scan
├── discard scratch
└── GC
```

如果 Scanner 支持并发，则需要进一步考虑：

```text
Scanner
    ↓
per-goroutine scratch
```

或者：

```text
sync.Pool
```

但不要为了减少 allocation 就直接引入 `sync.Pool`。

首先应该确认 allocation 来源。

# 二十、Rule #094 Required Literal 提取问题：实证与修复方向

> 本章节为追加章节，记录在执行本排查计划过程中发现的具体根因与修复方向。
> 文档前 19 节内容未做任何修改。
> 记录人：自动化排查流程
> 记录日期：2026-09-22

## 20.1 实证结论：Rule #094 是 150 MB alloc 的唯一主要来源

### 20.1.1 触发原理

`scankit` 在 `Compile` 阶段为每条规则提取一个"必须文字"（required literal）作为整块扫描前的快速候选索引。对于 Rule #094：

```
[+-]?[0-9]+(\.[0-9]+)?[eE][+-]?[0-9]+
```

由于 `[eE]` 是大小写字符类，编译器无法提取一个唯一的多字节 literal，因此 fallback 到把单字节 `e` 和 `E` 分别注册到 `requiredLiterals`。结果：

- `requiredLiterals[178]`、`requiredLiterals[179]` 都对应 Rule #094
- 两者都包含 required variant `"e"` 与 `"E"`，`min=1`、`max=-1`（无偏移上界）

### 20.1.2 为什么会在 10 MB 噪声下触发 ~1.5M 次 append

`buildBenchmarkCorpus(10MB, 0)` 生成的噪声文本是：

```
INFO request completed successfully message=hello world\n
```

这个 57 字节的字符串中，`e` 多次出现。整 10 MB / 57 ≈ 184,210 行 × 每行多个 `e` ≈ **实测 1,497,960 次** `e` 出现。

`newSingleByteFinder`（scanner.go:530-565）走 SIMD 字节集合扫描，每个 `e` 命中执行：

```go
dst = append(dst, requiredHit{slot: int(id) - 1, pos: off + bit})
```

由于 `dst` 来自 `ctx.requiredHits[:0]`，而 `ctx.requiredHits` 在 reset 阶段被以下逻辑处理：

```go
if cap(ctx.requiredHits) > 1<<20 {
    ctx.requiredHits = nil
} else {
    ctx.requiredHits = ctx.requiredHits[:0]
}
```

1.5M 次 append 必然让 cap 超过 1 MB，因此每次扫描都被置 nil，下次扫描又从 cap=0 重新 grow。

### 20.1.3 字节级量化

独立复现 grow 累计成本（相同的数据量与 append 模式）：

```
TOTAL single-byte hits: 1,497,960
fakeHit size = 16 bytes
TotalAlloc delta: 138,004,760 (131.61 MB) for 1,497,960 appends
per-hit cost: 92.13 bytes
final cap: 1,734,656 (cap*hitSize = 27,754,496 bytes = 26.47 MB)
```

**单次 `scanInto` 在 10 MB / 0 sample 下的 ~150 MB alloc 中，~131 MB 来自这里**，其余 ~20 MB 来自 `requiredScanStarts` 内部的 `starts` 增长、sort 缓冲分配等周边路径。

### 20.1.4 "假手术"验证

通过将 Rule #094 在 benchmark 规则集中注释（`hyperscan_go_100_rules_benchmark_test.go:202`），跑同一份 `BenchmarkEngineScan/10MB_0sampleMB`：

## 20.2 问题定性

这不是 Hyperscan 层面的问题，而是 `scankit` 的 required literal 提取算法对"大小写字符类 + 无偏移上界"组合的退化。具体包含三个互相叠加的因素：

1. **字符类 `[eE]` 退化为两个独立 single-byte literal**：编译器无法找到唯一的多字节 prefix，只能把每个字节单独注册。
2. **`max=-1` 无偏移上界**：candidate 命中位置之前的任意起点都被认为是潜在 match 起点，确认程序需要从所有起点出发验证。
3. **reset 策略放大分配**：`if cap > 1<<20 { nil }` 在 huge-append 场景下导致每次扫描都从 cap=0 重新 grow 而非复用。

任何一条独立都不致命，三者叠加才会产生 150 MB 的极端数字。

## 20.3 修复方向（按优先级排序，不动代码）

### 20.3.1 P0：禁止 `[eE]` 这类字符类被单独提为 required literal

`internal/parser` 或 `internal/prefilter` 在提取 required literal 时，如果候选是大小写字符类（character class），应回退到以下两种策略之一：

- **策略 A：合并到上下文**。把 `[eE]` 与其前后必然存在的 token（如 Rule #094 里的 `[0-9]+(\.[0-9]+)?`）合并成一个多字节 literal，例如 `\.e`、`\.E`、`+e`、`+E`，再交给 `splitRequiredLiterals` / `newLiteralMatcherFinder` 处理。这样 candidate 命中密度从 `e 在英文文本中 ~15%` 降到 `\.e` / `+e` 等罕见组合的近 0。
- **策略 B：不下发到 requiredIndex**。如果字符类无法安全合并（例如 `e` 出现在表达式的第一个 token），就让这条规则直接走 backend 整块扫描（`backendOnly=true`），不进入 requiredIndex。

实现位置：`internal/prefilter/prefilter.go` 的 `graphPrefix` 与 `scanner.go` 的 `buildRequiredIndex`。

### 20.3.2 P1：`splitRequiredLiterals` 给 single-byte literal 加密度阈值

在 `scanner.go:512-522` 的 `splitRequiredLiterals` 之后、`newSingleByteFinder` 之前插入一道"输入密度预估"：

```text
candidateBytes := 扫描 N KB 样本，统计 single-byte literal 集合中每个字节的命中频率
if max(freq) > threshold (e.g. 5%):
    把这些 byte literal 标记为 high-density
    high-density 的 literal 不进入 newSingleByteFinder，转交 backend 整块扫描
```

为什么是 5%：英文文本里 `e` 约 12.7%、空格约 18%、`t` 约 9%，任何常见字母/空格都超过 5%。这种阈值可以让 Rule #094 的 `[eE]` 自动 fallthrough 到 backend 路径。

实现位置：`scanner.go` 的 `newRequiredFinder` 或外层 `newScanner`。

### 20.3.3 P2：`requiredHits` 的 reset 策略改进

`scanner.go:1387-1391`：

```go
if cap(ctx.requiredHits) > 1<<20 {
    ctx.requiredHits = nil
} else {
    ctx.requiredHits = ctx.requiredHits[:0]
}
```

问题：当 `requiredHits` 在某次扫描增长到 ~16 MB 后，下次扫描无论输入是否含 `'e'` 都会从 cap=0 重新 grow。改进方向：

- 保留一个"历史最大 cap"在 `scanContext` 上，reset 时把 `cap` 截断到 `max(cap, min(previous, 1<<20))`，避免每次从 0 开始。
- 或者改为 `cap > data_length × 32` 才释放（按输入大小动态调整）。

这条优化的收益取决于 P0/P1 是否生效；如果 P0 让 `[eE]` 不再进 requiredIndex，`requiredHits` 的高水位会自动降下来。

### 20.3.4 P3（可选）：Rule #094 改写为不依赖大小写字符类

直接修改 Rule #094 模式为：

```
[+-]?[0-9]+(\.[0-9]+)?(e|E)[+-]?[0-9]+
```

让编译器能识别出 `(e|E)` 仍然是字符类，但可能通过 NFagraph 的 normalize 步骤变成 alternation，进而能提取一个稳定的多字节 prefix（取决于 normalize 实现）。这是规则集层面的 workaround，**不推荐作为正式修复**，因为规则集是由 `vectorscan-source-map.md` 锁定的参考设计。

## 20.4 修复方案选型建议

| 方案 | 收益 | 风险 | 改动范围 |
|---|---|---|---|
| **P0 策略 A**（合并上下文） | 根本消除 single-byte literal | 需要正确处理字符类归一化 | parser / prefilter |
| **P0 策略 B**（不下发） | 简单、改动小 | 高密度场景下 backend 路径成本上升 | scanner.go:421-444 |
| **P1（密度阈值）** | 自适应、通用 | 阈值选取需要大量样本验证 | scanner.go:486-510 |
| P2（reset 策略） | 边际收益 | 不解决 root cause | scanner.go:1387-1391 |

推荐组合：**P0 策略 B + P1**。策略 B 把 Rule #094 这种已知问题规则直接 fallthrough；P1 给其他类似的字符类规则兜底。P2 视实际数据再决定。

## 21.2 ctx reset 后的 cap 状态

扫描完成后从 pool 中取出 ctx，记录 reset 之后的 cap：

```
requiredHits   cap=570,880 entries  (8.71 MB raw)  ← reset 保留（cap < 1<<20）
requiredStarts cap=0                (0)            ← reset 释放（cap > 1<<20）
```

`ctx.directMatches` 的 reset 逻辑位于 scanner.go:1395-1417 的 defer 块中——**完全没有针对 `directMatches` 的释放策略**，所以 cap 跨扫描保留复用。

## 21.3 用户原假设的修正

先前排查中曾猜测："高密度下 matches slice 自身的扩容会成为新瓶颈"。**这个假设是错的**：

- `ctx.directMatches` cap=241,322（5.52 MB）跨扫描保留，warm 状态下每次分配 = 0
- cold 状态下首次分配 ~27 MB（grow from cap=0 to 241K），但这是单次成本
- **真正每次都从 cap=0 重新分配的是 `requiredStarts`**，因为 reset 策略在 cap > 1<<20（即 > 1M entries，约 8 MB raw）时释放

## 21.5 grow 累计因子

独立 grow 模拟（cap=0 → target N）：

| target entries | uint64 alloc | raw data | 因子 |
|---|---:|---:|---:|
| 570K | 25.26 MB | 4.6 MB | **5.5×** |
| 1M | 39.75 MB | 8.0 MB | **5.0×** |
| 1.5M | 62.41 MB | 12.0 MB | **5.2×** |
| 2M | 78.16 MB | 16.0 MB | **4.9×** |

Go slice geometric grow 产生稳定 **~5× 累计因子**（每次 grow ≈2×，加 size class 对齐）。这意味着：

- raw data N bytes → 累计 alloc ~5N bytes
- 229K matches × 24 bytes = 5.5 MB raw → cold 扫描累计 ~27 MB（仅首次，warm 后复用 0 alloc）

## 21.6 110 MB 精确归因

按 reset 策略推断每次扫描的 grow 起点：

| 路径 | 起点 cap | 终点 cap（推断） | raw 增量 | 单次 alloc 累计 |
|---|---:|---:|---:|---:|
| `requiredHits` | 0（cold）/ 570K（warm） | 570K | 8.7 MB | ~43 MB（cold）/ 0（warm，cap 够） |
| `requiredStarts` | **0（每次）** | ~2M-2.5M | 16-20 MB | **~80-100 MB** |
| `directMatches` | 0（cold）/ 241K（warm） | 241K | 5.5 MB | ~27 MB（cold only）/ 0（warm） |
| `appendGuardRunStarts` emitRun | 跟随 requiredStarts | 跟随 | 包含在 starts 里 | ~25 MB |

**`requiredStarts` 占稳态分配的主导**：每次扫描 cap 都从 0 grow 到约 2M entries（>1M entries 触发 reset 释放），累计 ~80-100 MB alloc。

## 21.7 三个独立修复点（按优先级）

### P1：`requiredStarts` 的 reset 阈值调整

**当前**（scanner.go:1389-1391）：

```go
if cap(ctx.requiredStarts) > 1<<20 {  // > 1M entries ≈ 8 MB raw
    ctx.requiredStarts = nil
} else {
    ctx.requiredStarts = ctx.requiredStarts[:0]
}
```

**问题**：10000 sample 下 requiredStarts 增长到约 2M entries（16 MB raw），超过阈值被释放。下次扫描又从 0 grow 累计 ~80-100 MB。

**修复方向**：

- 简单方案：提高阈值到 `1<<24`（>16M entries），让绝大多数 case 不触发释放
- 自适应方案：`cap > data_length × 8 / 8 = data_length` 才释放，按数据大小调整
- 激进方案：直接不释放，让 cap 自然增长到稳态

### P2：`directMatches` 加 reset 策略

**当前**（scanner.go:1395-1417）：无 `directMatches` 释放策略 → cold 扫描首次分配 ~27 MB grow 累计；warm 复用 0 alloc。

**问题**：在并发场景下每个 goroutine 冷启动一次，会累积大量内存峰值。

**修复方向**：跟 `requiredStarts` / `requiredHits` 一致加 reset 策略：

```go
if cap(ctx.directMatches) > 1<<18 {  // > 256K entries ≈ 6 MB
    ctx.directMatches = nil
} else {
    ctx.directMatches = ctx.directMatches[:0]
}
```

但 P2 是 cold-start 优化，对 warm 状态无影响。

### P3：`appendGuardRunStarts` 的 emitRun grow 优化

**当前**（scanner.go:2176-2181）：

```go
starts := emitter.starts
if cap(starts)-len(starts) < count {
    starts = slices.Grow(starts, count)
}
base := len(starts)
starts = starts[:base+count]
```

`emitRun` 把 guardRun 命中段展开为 starts，累计 ~25 MB alloc。修复方向是预先按段长度 `count` 一次性 grow 到合适大小，避免段内逐元素 grow 的累计因子。

## 21.8 修复效果预估

| 场景 | 当前 B/op | 修复 P1 后预估 | 修复 P1+P2+P3 后预估 |
|---|---:|---:|---:|
| 10MB_10000sample | 111 MB | **~30 MB** | **~10 MB** |

P1 单独就能省 80 MB（`requiredStarts` 占大头）。剩下 30 MB 主要是 cold 扫描首次 grow + 其他 helper。

## 21.9 与 §20.6 的关系

§20.6 提到"高密度段仍然受 `directMatches` grow 影响，这一部分仍待排查"。本章节实证结论：

- `directMatches` grow 在 warm 状态下分配 = 0（cap 保留复用）
- **真正每次都触发 grow 的是 `requiredStarts`**，而非 `directMatches`
- §20.6 的猜测方向部分正确（"高密度 grow"），但具体路径需要修正（从 `directMatches` 改为 `requiredStarts`）

## 23.2 主循环：`confirmCandidatesAndFallback`（核心瓶颈）

文件：`scankit/scan_start_bytes.go:116-184`


**10 MB 输入 = 10,485,761 次循环迭代**。每次迭代：

1. `st.data[start]` 单字节读（无 SIMD）
2. `index.groupOf(...)` 计算（`int(data[start])`，取值 0-255）
3. `index.rulesAt(group)` 切片访问，返回 `width = (len(rules)+63)/64` 个 uint64
4. 遍历每个 word，提取 set bits，调用 `st.verify(rule, start)`

**没有 8 字节 word scan**。每次迭代都是单字节读 + 切片查找。

## 23.3 scankit_main 的对应实现：`scanBlockSingleByteAnchorWord`

文件：`scankit_main/scanner.go:2366-2436`（用户参考路径）

```go

                } else {

                }
            }
            ...
        }
    }
    for ; offset < len(data); offset++ { ... }                     // ← 尾部逐字节

```

**核心 SWAR 操作**（`fast_bytes_unsafe.go:31`）：

```go
func byteWordMatchMask(word uint64, value byte) uint64 {
    xor := word ^ uint64(value)*byteWordOnes                  // value 广播到 8 字节
    return (xor - byteWordOnes) &^ xor & byteWordHigh          // SWAR 借位 mask
}
```

**1 个 ALU 操作 = 8 个字节的相等性检测**。

## 23.4 借鉴改造方案（按 ROI 排序）

### 改造 1：把 8 字节 SWAR word scan 加到 `confirmCandidatesAndFallback`（**最高 ROI**）

**当前**（scan_start_bytes.go:138）：

```go
for start := 0; start <= len(st.data); start++ {
    row := index.rulesAt(index.groupOf(st.data, start))
    ...
}
```

**改造后**（伪代码）：

```go
// 对每个 rule 预先准备 SWAR byte set
type ruleSWAR struct {
    ruleIdx    int
    masks      []uint64  // 每个 firstByte 一个 SWAR mask（已预计算）
}

// 主循环：对 8 字节 word 做并行比较
for offset := 0; offset+8 <= len(data); offset += 8 {
    word := binary.LittleEndian.Uint64(data[offset:])

    // 计算哪些 rule 在这 8 字节内有候选起点
    var triggerMask uint64 = 0
    for _, rs := range rulesSWAR {
        ruleMask := uint64(0)
        for _, m := range rs.masks {
            ruleMask |= m & byteWordMatchMask(word, ...)
        }
        if ruleMask != 0 {
            triggerMask |= ruleMask
            // 记录 (ruleIdx, bitPosition) 等待 verify
            ...
        }
    }

    if triggerMask == 0 { continue }  // 8 字节 0 触发 → 整批跳过

    // 逐位处理触发位置
    for triggerMask != 0 {
        bit := bits.TrailingZeros64(triggerMask)
        triggerMask &= triggerMask - 1
        ...
    }
}
```

**预期收益**：Phone1/Email 等 pattern 的 `scanInto` 时间降到 scankit_main 量级（**44%-168% 提速**），因为：

- 10MB 输入循环次数从 10,485,761 降到 1,310,720（×8 倍）
- 无触发区域（"INFO request completed..."）几乎不消耗 CPU

**风险**：复杂度上升，需要小心 word 边界 + 末尾 < 8 字节的逐字节 fallback。

### 改造 2：增加编译期路径选择（blockScanPlan）—— 12+ scanBlock 函数（**次高 ROI**）

**当前**（scanner.go:1302-1580）：4 条主路径。

**改造后**：参照 scankit_main 增加 `blockScanPlan` 字段，编译期根据 pattern 形状选择路径：

```go
type blockScanPlan struct {
    directLiterals     bool  // 纯字面量规则
    singleByteOnly     bool  // 仅单字节锚点
    singleByteFast     bool  // 单字节且无 lookaround
    singleByteSimple   bool  // 仅单个匹配规则
    singleByteValues   [8]byte
    rootByteFast       bool  // 根字节可特化
    fixedOnlyBlock     bool  // 仅固定长度规则
    simpleRepeatOnly   bool  // 仅简单重复规则
    mixed              mixedPlan
    wordScan           bool  // 是否启用 word scan
}
```

然后 `scanBlock` 内根据 plan 分派到专门的函数（每个函数都是高度特化的热路径）。

**预期收益**：
- Phone2/Phone3/ChineseID/CreditCard 等含 lookaround/word boundary 的 pattern 也能走特化路径
- 路径选择从编译期 4 种扩到 12+ 种

**风险**：改造成本大，需要重写大部分 scanInto。

### 改造 3：Aho-Corasick 引擎作为统一入口（**架构性改造**）

**当前**：HWLM (teddy/noodle/fdr) + NFA/DFA/Rose 多引擎。

**改造后**：所有 pattern 都先编入 Aho-Corasick 自动机，AC 输出后再 confirm：

```
AC 扫描
  ↓ 输出触发 (offset, ruleIndex)
确认程序
  ↓ 输出 match
```

**预期收益**：
- 短字符类 pattern 走 AC + 立即 append（无 confirm）
- 多 pattern 综合（AllPIITypes）走 AC 一次性匹配
- 路径统一，调试和维护成本降低

**风险**：AC 对长字符类（ChineseID）状态数爆炸，需要限制字符类宽度。

## 24.1 选型：先否掉策略 B，再落地策略 A

§20.4 推荐的是「P0 策略 B + P1」。本次先按策略 B 做了最小实现（在 `FromAST` 阶段直接拒绝"完全由字符类展开出的单字节"计划），实测回退代价不可接受：

| 场景 | 策略 B（Rule #094 不进索引） | §22 基线（Rule #094 注释） | 修复前（Rule #094 进索引） |
|---|---:|---:|---:|
| 10MB_0sampleMB ns/op | 52,623,555 | 36,433,038 | 44,841,131 |
| 10MB_0sampleMB MB/s | 190.03 | 274.48 | 223.01 |

原因可以精确定位：

- Rule #094 编译后 `backendEligible=false`（非定长、NFA 非独立），无法走整块后端扫描。
- Rule #094 的 `guard == nil`，`guardRunFor` 不成立，无法改由前缀字节约束枚举。
- 于是它只能落进 `confirmUncoveredRules`，使 `scanner.startBytes` 非空。
  `confirmCandidatesAndFallback` 会因此对整块数据多做一次 `0..len(data)` 的位置遍历，
  10 MB 下约增加 16 ms。

也就是说，策略 B 把「候选文字命中过多」换成了「整块逐位置遍历」，在 10 MB 量级上得不偿失。

因此本章实现的是 **P0 策略 A（合并到上下文）**：把字符类展开出的单字节候选与前序元素末尾**必然出现**的字节合并为多字节候选，让 Rule #094 继续留在必须文字索引内。

## 24.2 实现：候选文字左合并

改动集中在 `internal/prefilter/required.go`，共四处：

1. **候选来源标记**。新增 `literalStep{value, class}` 取代原来各处传递的裸 `[]byte`；
   `parser.Class` 展开出的候选标记 `class=true`，字面量字节标记 `false`。`crossProduct`
   拼接时按位或合并来源标记，因此"多字节但含类字节"的候选不会被误判为弱候选。

2. **末尾候选推导**。新增 `trailingLiterals` / `trailingLiteralsOfNode` / `trailingUniform`：
   从序列末尾向前找到最后一个必须消费字节的元素，给出"紧跟在下一位之前必然出现"的文字集合。
   集合中的候选是**或**关系，因此：

   - 末尾元素非空匹配时，其末尾候选来自该元素自身；
   - 末尾元素可空时，它空匹配的分支由更早的元素决定末尾字节，两条分支的候选必须**取并集**；
   - 零宽节点（断言、控制动词、环视）直接跳过；
   - 节点只能匹配空串、或重复体的子节点可空（最后一次迭代可能整体为空）时返回「无法推导」。

   并集会重复贡献同一文字（`[0-9]+(\.[0-9]+)?` 就是典型），因此统一做内容去重后再进入打分。

3. **左合并**。`sequencePlan` 新增闭包 `consider(steps, min, max, back, trail, trailLen)`：
   原始候选照常登记；当候选退化为"完全由字符类展开出的单字节"形态（`classOnlySingleByte`）时，
   再把末尾候选整体前置，生成一组多字节合并候选：

   ```
   mergedValue  = trailValue + stepValue
   mergedMin    = min - trailLen      // 仅当 min >= trailLen 时合并
   mergedMax    = max < 0 ? max : max - trailLen
   ```

   合并候选与原候选**同时参与 `planScore` 打分**，只有总分更高时才替换，
   其余模式的提取结果因此保持不变。

4. **不改变语义的兜底**。合并未能成立（无末尾候选、`min < trailLen`、笛卡尔积超过
   `maxVariants`、合并结果超过 `maxLiteralBytes`）时，原候选仍然保留，
   规则行为与修复前完全一致。

# 二十五、§21.7 P1 实施：候选起点与文字命中缓冲的池内保留策略

> 本章记录 §21.7 P1 的落地实现、归因实验与量测。§24 解决的是 Rule #094 的候选文字提取，
> 本章解决的是 10MB_10000sampleMB 场景里残留的 150 MB/scan 分配。

## 25.1 问题与实现

§21.6 的归因结论是 `requiredStarts` 每次扫描都从 cap=0 重新 grow。原实现（scanner.go:1389-1391）
使用固定阈值：

```go
if cap(ctx.requiredStarts) > 1<<20 {  // > 1M entries
	ctx.requiredStarts = nil
} else {
	ctx.requiredStarts = ctx.requiredStarts[:0]
}
```

10MB 密集输入的稳态容量约 2,581,504 条目（大于 1<<20），因此**每次扫描都命中"释放"分支**，
下次扫描再从 0 grow 到 2.5M，累计分配约为数据量的 5 倍。这不是"偶尔释放"，而是恒定生效。

新策略把阈值改为随输入长度缩放，同时保留一个绝对上限（scanner.go:200-229）：

```go
const (
	bufferRetainScale         = 8
	bufferRetainFloor         = 1 << 13
	requiredStartsRetainLimit = 1 << 22
	literalMatchesRetainLimit = 1 << 22
)

func retainWithinInput(capacity, dataLen, limit int) bool {
	if capacity > limit {
		return false
	}
	return capacity <= bufferRetainScale*dataLen+bufferRetainFloor
}
```

- 容量与本次输入同阶（`<= 8*len(data)+8K` 条目）时保留复用；
- 同一个池随后处理明显更小的输入时释放，避免长期驻留相对过大的缓冲；
- 绝对上限 1<<22 条目之外一律释放（`[]uint64` 约 32 MB，`[]literalCandidate` 约 96 MB）。

### 25.1.1 同一缺陷的其它站点

`newLiteralMatcherFinder` / `newLiteralCandidateFinder`（teddy、fdr、noodle 各两处，共 6 个站点，
scanner.go:612-722）原本使用同一个固定阈值 `cap(matches) > 1<<20`，与 `requiredStarts` 属同源缺陷，
因此一并改用 `retainLiteralMatches`。

## 25.2 归因实验

为确认收益来自哪一处改动，把两处开关组合成 4 个配置逐个编译运行。量测口径是
`runtime.MemStats` 的 `TotalAlloc` 增量 / 50 次扫描（扫描前热身 10 次，配置之间间隔 10 秒）：

| requiredStarts=旧, literalMatches=新 | 1,571,850 | 2,785,472 | 146,476,161 |
| requiredStarts=新, literalMatches=旧 | 675,787 | 1,657,732 | 6,744,495 |
| requiredStarts=新, literalMatches=新 | 896,062 | 2,221,640 | **6,744,495** |

（d 为每 MiB 的样本密度，数据固定 10 MB。）

结论：

1. **收益全部来自 `requiredStarts`**：d=10000 从 143.8 MB/op 降到 6.74 MB/op（21 倍）。
2. 只改 `literalMatches`（第 2 行）没有收益 —— 这些密度下文字命中缓冲的容量没有超过 1<<20 条目，
   旧阈值从未触发。该改动是防御性的一致化，不是本章的收益来源。
3. 两处同时改（第 4 行）与只改 `requiredStarts`（第 3 行）在 d=10000 上数值完全相同，
   同样说明 `literalMatches` 在本 benchmark 中不触发。

# 二十六、池内保留判据收敛：从"按输入缩放"改为"只看绝对上限"

> 本章接续 §21.7 P1 / §25。§25 用的判据是"容量与本次输入同阶才保留"，本章的交替负载
> 实验证明它会把"大输入 → 小输入 → 大输入"变成每次大扫描都整块重新 grow，因此把判据
> 收敛为"只看绝对上限"，并把 §21.7 P2 的 `directMatches` 与 `requiredHits` 的固定阈值
> 一并统一。§25.1 的缩放判据由本章替换。

## 26.1 触发实验：混合尺寸的交替负载

同一个 Scanner 先以 10MB_10000sampleMB 热身 5 次，关闭 GC（`debug.SetGCPercent(-1)`）后
重复 `[10MB_10000sampleMB, 1KB_10sampleMB × 3]`，用 `runtime.MemStats.TotalAlloc` 逐次记录
每次扫描的分配：

| 扫描 | §25 缩放判据 | §26 绝对上限判据 |
|---|---:|---:|
| 第 1 次大输入（GC 清空池之后） | 203,690,792 | 203,687,464 |
| 小输入 ×3 | 992 / 2,952 / 984 | 3,408 / 952 / 944 |
| 第 2 次大输入 | **147,120,304** | **944** |
| 第 3 次大输入 | **147,120,304** | **944** |
| 小输入 ×3 | 992 / 2,952 / 984 | 952 / 944 / 944 |

原因：缩放判据在 1KB 小输入归还缓冲时判定"容量 2,581,504 条目远大于本次输入"→ 释放，
下一次 10MB 扫描必须从 0 重新 grow，单次 147 MB —— 与 §21.6 记录的原始缺陷同量级。
绝对上限判据下，池被 GC 清空后只付一次 203 MB 重建，之后不管尺寸怎么变都是 ~944 B/次。

## 26.2 收敛后的判据与统一范围

```go
const (
	requiredStartsRetainLimit = 1 << 22
	literalMatchesRetainLimit = 1 << 22
	requiredHitsRetainLimit   = 1 << 22
	directMatchesRetainLimit  = 1 << 22
)

// retainBuffer 是保留判据本身：容量不超过绝对上限即保留。
func retainBuffer(capacity, limit int) bool { return capacity <= limit }
```

- `requiredStarts` / `literalMatches`：替换 §25 的缩放判据；
- `requiredHits`：原为固定阈值 `cap > 1<<20`。固定阈值同样是"切一刀"，命中超过 100 万条的
  输入会退化成"每次扫描都释放、下次重新 grow"；
- `directMatches`：原无任何上限（§21.7 P2），现按同一判据保留 / 释放。

保留内存由两道约束兜住：绝对上限 1<<22 条目（`requiredStarts` 约 32 MB、`requiredHits`
约 64 MB、`directMatches` 约 96 MB），以及 sync.Pool 在 GC 时清空池的语义 —— 池对象最多跨
两个 GC 周期就被回收，"一次大扫描永久占住内存"不成立。

## 26.3 量测

交替负载（§26.1）：每次大扫描 147,120,304 B → **944 B**。

标准基准 TestEngineScanStable（10MB 五档，`allocs/op` 全部保持 0）：

## 26.5 结论与后续

- §21.7 P1 的目标（稳态零分配）保留：10MB 五档 `allocs/op` 仍为 0；

# 二十七、§23 归因复核：PII 瓶颈在候选起点枚举，不在确认循环

> §23 判定 PII 场景的瓶颈是 `confirmCandidatesAndFallback` 的逐字节主循环，并据此把
> "改造 1：加 8 字节 SWAR word scan"列为最高 ROI。本章用 CPU profile 复核该判断，
> 结论是**不成立**：热点在 `requiredScanStarts → appendGuardRunStarts` 的约束窗口扫描与
> 连续段展开。据此实施的针对性优化让 Phone1 系列提速 17~23%，其余场景持平。

必须从候选起点枚举这条路径下手。

## 27.2 成因

`guardRunGroup.appendStarts` 对每个宽窗口（64 字节）做三件事：

1. 求窗口内"约束字节集合"的 NEON 掩码；
2. 用 `mask &^ (mask<<1)` / `mask &^ (mask>>1)` 配对出极大连续段的起点位/终点位；
3. 每个连续段调用一次 `emitRange`，再由 `emitRun` 把段内每个成立的窗口起点展开成候选键。

日志语料里数字连续段极短（时间戳被 `-`、`:`、`.` 切成 2~4 位数字），而这些段每个都要付
一次 `emitRange` 调用（函数入口 + 切片头加载 + 循环判断），随后才发现"段长 < 窗口长度"
直接返回。

## 27.3 优化：先比段长，再展开

- `guardRunGroup` 增加 `minLength`（= `runs[0].length`，编译期在 `groupGuardRuns` 里算好）；
- `guardRunWindow.process` 配对出 `[beginBit, endBit]` 后先比较段长：

```go
// 段长不足组内最短窗口时没有任何起点成立，直接跳过展开调用。
if endBit-beginBit+1 < window.group.minLength {
	continue
}
window.emitRange(off+beginBit, off+endBit+1)
```

语义等价性：`emitRange` 的首条判断 `if run.length > length { break }` 在段长不足最短窗口时
本来就会立即返回，且没有任何副作用（`emitRun` 只在 `count > 0` 时写缓冲）。`minLength`
取零值（未设置）时判断恒不成立，行为退回原实现。

## 28. Email/NoMatch：确认窗口内的重复求值消除

### 28.1 定位（§23.7 遗留项）

§23.7 把 Email/NoMatch 列为与 scankit_main 差距最大的场景（168%，5,851 vs 2,181 ns/op）。
§27 用 CPU profile 复核 Phone1 时证伪了「确认循环」假设；本轮对 Email 做同样的取样：

```bash
go test -run '^$' -bench 'BenchmarkPIIRedaction/Email/NoMatch/EngineMask$' -benchtime 100000x -cpuprofile /tmp/pii_email.prof .
```

profile（680 ms 样本）分布与 Phone1 完全不同：

| 函数 | flat% | cum% |
|---|---:|---:|
| `(*confirmProgram).run` | **58.82** | 58.82 |
| `internal/graph.(*Directed).Vertices` | 5.88 | 7.35 |
| `internal/bytealg.IndexByteString` | 5.88 | 5.88 |
| `(*Scanner).requiredScanStarts` | 2.94 | 10.29 |
| `(*blockScanState).confirmCandidatesAndFallback` | 1.47 | **64.71** |
| `(*blockScanState).verify` | 1.47 | **63.24** |

- `Vertices` 的调用者是 `nfagraph.BypassEpsilonJoins` / `MergeEquivalentNodes`，即**编译期**
  的 NFA 化简，属于基准 fixture 装配噪声，不在扫描热路径上；
- Phone1 的瓶颈是候选起点枚举（`guardRunWindow.process`、`nativeByteSetMask32`），
  Email 的瓶颈**完全落在确认路径**：`verify` → `preferredEnd` → `confirmProgram.run`。

把候选起点与确认求值拆开单独计时（同一份 128 行 NoMatch 语料）：

| 量 | 数值 |
|---|---:|
| 候选起点数 | 128 |
| 确认求值次数 | 128 |
| 确认求值总耗时 | 4,266 ns/scan |
| 单次求值 | 33.3 ns |

候选起点数远大于文字命中数（32 个 `@` 命中），确认程序被重复执行了 4 倍。

### 28.2 根因

`logEmailPattern` 的局部部分是可重复字符类 `[A-Za-z0-9.!#$%&'*+/?^_`{|}~-]{1,64}`，
必须文字只提取到 `@`（偏移窗口 `[1,64]`，并携带左侧回退集合 `Back`）。
`requiredScanStarts` 在 `@` 命中位置的左侧沿 `Back` 回溯到连续段起点，再把窗口
`[left, hit-1]` 整段展开成候选起点——NoMatch 语料的局部部分是 `user`，一次命中摊开
4 个起点，32 个命中共 128 个起点。

这 128 个起点对应的确认程序**入口指令完全相同**：`confirmOpSetRepeat(set=局部部分字符集,
min=1, max=64)`，且该集合与 `Back` 逐字节一致、入口文字首字节 `@` 不属于该集合。
于是从窗口内任意起点 `s` 出发：

- `[left, hit)` 全部属于该集合、`hit` 处的 `@` 不属于该集合，重复必然停在 `hit`；
- 窗口下界保证 `hit-left ≥ min`、上界保证 `hit-left ≤ max`，重复不会因上下界截断；
- 重复为更短消费长度压入的回溯帧落在 `[s+min, hit-1]`，那里都是集合内字节，
  与入口文字 `@` 必然不等，因此帧全部失败，与 `s` 无关。

结论：窗口内所有起点共享同一个「偏好结束偏移」结果，逐起点重跑确认程序是纯重复开销。

### 28.3 方案决策：为什么不是「只枚举最左起点」

最直接的改法是让 `requiredScanStarts` 对这类窗口只产出一个起点。实测**不可行**：
块模式允许同一规则产生重叠命中，`verify` 用 `blockedUntil` 做抑制，而抑制是在**候选
遍历阶段按起点升序**生效的。若窗口最左起点被前一个命中抑制，正确的下一个命中应该从
`blockedUntil`（前一个命中的结束偏移）处开始——它位于窗口内部，删掉它就漏报：

```
data = ":e ..@909bZ.zbz.9-!!@9zA." + "q"*63 + ".0az9.9Z"
Go regexp   : [{1,3,17} {1,17,96}]
只保留最左起点: [{1,3,17}]          ← 第二个命中丢失
```

因此最终方案**不改候选枚举**，只在确认求值时复用结果：`verify` 先看当前起点是否落在
该规则上一次求值登记的窗口内，命中则直接复用，否则求值并把窗口登记下来。候选起点、
遍历顺序、`blockedUntil` 抑制逻辑全部保持原样，语义上与原实现逐位等价。

实现要点（`scanner.go`）：

| 位置 | 内容 |
|---|---|
| `collapseHead` / `newCollapseHead` | 构造期判定入口重复是否满足「集合等于 `Back`、上下界等于窗口、文字首字节不在集合内」，并要求窗口内只有一个必须文字变体、`guard` 完全由 `Back` 保证、`confirmSkip` 为 0 |
| `collapseHead.runEnd` | 求重复的结束位置；连续段长于重复上界时返回 -1（重复被上界截断，尾程序起点随起点变化，窗口不成立） |
| `verify` | 窗口命中则复用 `memo.end`，否则 `confirmEnd` 求值后 `recordCollapseWindow` |
| `recordCollapseWindow` | 仅在 `ok == true && end < 0`（预算内正常返回且未命中）时登记。命中时 `record` 会把 `blockedUntil` 推到匹配结束位置，窗口内更靠右的起点在候选阶段已被重叠抑制，登记无收益、反而多付一次连续段扫描 |
| `reserveCollapseWindows` | 缓存按规则下标存放在 `scanContext`，随上下文池复用；`Scanner.hasCollapse` 为假时不分配 |

### 29.2 实现一：64 字节半字节查表内核 `nativeByteSetMask64`

内核逐位语义与 32 字节版本完全一致（同一份常量、同一份表、同一组 VUSHR/VTBL/VCMHS/
VBSL/VUSHL/VCMTST 序列），只是把「装载 + 量化」从每 32 字节一次降为每 64 字节一次。

### 29.3 实现二：单字节候选文字改用 memchr

`newSingleByteFinder`（`scanner.go`）原本一律用「字节集合扫描 + 256 项查表」求单字节
候选文字的全部命中位置。字节集合扫描对**任意**集合都只扫一遍，但每个 64 字节窗口都要
付一次半字节查表与常数量化的固定成本；`memchr` 的常数小得多，代价却随文字数线性增长。

微基准（26.5 KB 合成日志、2 个单字节文字、`-benchtime 20000x`）：

| 路径 | ns/op | MB/s |
|---|---:|---:|
| `newSingleByteFinder`（字节集合扫描） | 3,071 | 8,639 |
| 逐文字 `bytes.IndexByte` | **1,183** | **22,425** |
| `WindowMask64` 单趟纯粹扫描（对照） | 2,236 | 11,863 |

集合扫描 ≈ 2.2 µs/趟（与文字数无关），memchr ≈ 0.59 µs/文字，成本交点约在 4 个文字。
据此新增阈值 `singleByteFinderMemchrLimit = 4`：文字数不超过阈值时逐文字 memchr，
否则退回集合扫描。两种策略的命中顺序不同，但 `requiredScanStarts` 只做计数上限判定
并把全部命中展开后统一排序，顺序不参与语义，因此可以互换。

### 29.6 被证伪的尝试：窗口配对快路径（已回退，不在代码中）

**假设**：`guardRunWindow.process` 里「枚举每个连续段起点/终点位再比长度」是稀疏语料上
最大的确定性开销，只要先用一次「幂次位移与」判掉「窗口内没有长度达标的连续段」的窗口，
就能整段跳过配对循环。

**实测**：不成立，两版判定都没能赚回自身成本。

| 版本 | 判定语义 | Phone1/NoMatch | LowMatch | HighMatch | AllPIITypes/NoMatch |
|---|---|---:|---:|---:|---:|
| 弱必要条件（位移 1/2/4，直接与 `mask`） | 保留大量 6 位数字段，几乎总是回落完整配对 | 4,878 vs 4,623（**+5.5%**） | +6.8% | +5.3% | −0.5% |
| 逐级加倍 + 末位位移（`minLength=9` 时精确） | 只在真有 9 位连续段时回落 | 4,629 vs 4,634（−0.1%） | +1.1% | −1.8% | +0.3% |

原因：`guardRunWindow.process` 每窗口只有约 4 ns（24.5 KB 语料 383 个窗口、整段配对
合计约 1.5 µs/scan），而一次 6–8 条整数运算的判定本身就要 1–2 ns/窗口，两者同量级；
profile 里 `process` 的 25% flat 是**相对占比**，不是可回收的绝对量。第二版虽然把判定
收紧到精确，仍只在噪声内浮动，因此整段回退，避免为噪声增加一条必须长期维护的正确性
分支（尤其它涉及跨窗口接力段的不变量）。

保留的价值：验证过程中发现了 `process` 的两条隐含不变量并写成断言级测试——
「`runStart >= 0` ⟹ 下一窗口 bit 0 必然命中」、「`runStart >= 0` 且窗口内无达标段 ⟹
接力段必在本窗口内结束」，以及新增的随机差分测试（见 29.4）。

### 29.7 结论与后续

- 本轮落地两处优化：64 字节半字节查表内核（Phone1/NoMatch −4.9%）、单字节候选文字

- 候选枚举侧的「整段扫描」改造已告一段落，剩余唯一明显落后档位是 `Email`

- `Email` 的热点已不在候选枚举：确认程序 `confirmProgram.run` 占 34.57% flat，其中
  取指（`instr := p.instrs[pc]`）与 `switch instr.op` 两项合计约占该函数 56%，是解释器
  调度开销而非匹配逻辑开销；`requiredScanStarts` + `verify` 合计约 21%（每个 `@` 命中

  逐候选确认常数明显更小。下一步若继续压缩 Email，方向是确认程序的调度改造或按规则
  生成小型 DFA，而不是继续在候选枚举侧找收益。

#### 30.3.5 lane 数的隐含不变量（一次误报的排查记录）

在做 lane 相关实验时，「所有扁平索引都改用 4 个 lane」的一次改动让
`BenchmarkEngineScan/10MB_1000sampleMB` 的 `matches/op` 从 23127 掉到 14228，表面看
像多 lane 掩码过度过滤（漏报）。逐层排查后确认**不是代码缺陷，是实验本身破坏了
lane 数的隐含不变量**：

- `noodle.New` 取 `m.lanes = min(最短文字长度, 4)`，lane 集合按
  `lane < 最短文字长度` 填充；lane 数一旦超过最短文字长度，超出的 lane 保持**空集合**，
  该 lane 的掩码恒为 0，按位与之后整个窗口掩码恒为 0，候选整段消失；
- 规则集里通常同时存在单字节必须文字（例如 `@`、`z`），这些匹配器的最短文字长度
  是 1，对它们强制 4 lane 就会漏掉全部候选。

把覆盖点改到「`New` 内部、lane 集合填充之前」（保持不变量），再跑随机差分：
文字长度 4/5/8 三档 × 每档 300 轮随机语料 × 标量逐字节 oracle，lane 取 1/2/3/4
**全部一致、零漏报**，说明 `strict | first&tail` 的多 lane 组合确实是正确超集。

结论：`lanes <= 最短文字长度` 是硬不变量，任何调整 lane 的代码路径都必须维持它。
§30.3.2 的实验只把 lane 数从 `min(最短文字长度, 4)` 收敛到 1，不破坏该不变量，
所以那一组数据有效；而「一律 4 lane」这种改法本身不成立，不能据此判断多 lane 有 bug。

#### 30.3.6 合并开放寻址槽位（无收益，已回退）

`flatTable.lookup` 在 profile 里占 10.77% flat、`keyAt` 占 4.98%，其中一次探测要读
两个数组（先读 `slots[index]` 拿槽号，再按槽号读 `keys[slot-1]` 取主键）。把两者合并成
一条 16 字节记录（`struct{ key uint64; bucket int32 }`，bucket 0 表示空槽）后同树 A/B：

| 指标（3 次中位） | 两条数组（当前） | 合并槽位 | 变化 |
|---|---:|---:|---:|
| EngineScan/10MB_0sampleMB（200x） | 15,728,470 | 15,543,261 | −1.2% |
| PIIRedactionRules100/HighMatch/ScannerScanInto | 253,393 | 255,604 | +0.9% |
| PIIRedactionRules100/HighMatch/EngineMask | 314,913 | 319,052 | +1.3% |

三项都在 ±1.3% 以内、方向还不一致，属于噪声；按「不为噪声增加复杂度」的既有原则
**回退**，保留原来的两条数组。注意这与 §30.5 第 2 条（把槽位拆成两条数组而变慢）
不是同一件事：拆分是「本来一条记录又拆开」而变慢，合并是「两条数组并成一条」而没有
变快——两种方向都试过，说明这一层的瓶颈不在槽位加载的 cache line 数上。

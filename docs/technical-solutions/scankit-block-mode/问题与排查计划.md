# 五、优先检查是否存在“按输入大小增长”的临时内存




```text

    ↓

    ↓

    ↓

```

这种情况需要重点确认。

# 七、检查 Scanner 是否每次 Scan 都重新构造执行状态

例如：

```go
func (s *Scanner) scanInto(data []byte, matches []Match) ([]Match, error) {
    states := make(...)
    ...
}
```

如果 `states`、`nodes`、`queue`、`visited` 等对象每次 Scan 都重新创建，需要判断：

1. 是否真的需要
2. 是否可以复用
3. 是否可以使用固定容量
4. 是否可以使用 stack / small buffer
5. 是否可以通过 Scanner 生命周期持有 scratch buffer

例如：

```text
Scanner
├── immutable compiled rules
├── reusable scratch
└── Scan
```

而不是：

```text
Scan
├── allocate scratch
├── scan
├── discard scratch
└── GC
```

如果 Scanner 支持并发，则需要进一步考虑：

```text
Scanner
    ↓
per-goroutine scratch
```

或者：

```text
sync.Pool
```

但不要为了减少 allocation 就直接引入 `sync.Pool`。

首先应该确认 allocation 来源。

# 二十、Rule #094 Required Literal 提取问题：实证与修复方向

> 本章节为追加章节，记录在执行本排查计划过程中发现的具体根因与修复方向。
> 文档前 19 节内容未做任何修改。
> 记录人：自动化排查流程
> 记录日期：2026-09-22

## 20.1 实证结论：Rule #094 是 150 MB alloc 的唯一主要来源

### 20.1.1 触发原理

`scankit` 在 `Compile` 阶段为每条规则提取一个"必须文字"（required literal）作为整块扫描前的快速候选索引。对于 Rule #094：

```
[+-]?[0-9]+(\.[0-9]+)?[eE][+-]?[0-9]+
```

由于 `[eE]` 是大小写字符类，编译器无法提取一个唯一的多字节 literal，因此 fallback 到把单字节 `e` 和 `E` 分别注册到 `requiredLiterals`。结果：

- `requiredLiterals[178]`、`requiredLiterals[179]` 都对应 Rule #094
- 两者都包含 required variant `"e"` 与 `"E"`，`min=1`、`max=-1`（无偏移上界）

### 20.1.2 为什么会在 10 MB 噪声下触发 ~1.5M 次 append

`buildBenchmarkCorpus(10MB, 0)` 生成的噪声文本是：

```
INFO request completed successfully message=hello world\n
```

这个 57 字节的字符串中，`e` 多次出现。整 10 MB / 57 ≈ 184,210 行 × 每行多个 `e` ≈ **实测 1,497,960 次** `e` 出现。

`newSingleByteFinder`（scanner.go:530-565）走 SIMD 字节集合扫描，每个 `e` 命中执行：

```go
dst = append(dst, requiredHit{slot: int(id) - 1, pos: off + bit})
```

由于 `dst` 来自 `ctx.requiredHits[:0]`，而 `ctx.requiredHits` 在 reset 阶段被以下逻辑处理：

```go
if cap(ctx.requiredHits) > 1<<20 {
    ctx.requiredHits = nil
} else {
    ctx.requiredHits = ctx.requiredHits[:0]
}
```

1.5M 次 append 必然让 cap 超过 1 MB，因此每次扫描都被置 nil，下次扫描又从 cap=0 重新 grow。

### 20.1.3 字节级量化

独立复现 grow 累计成本（相同的数据量与 append 模式）：

```
TOTAL single-byte hits: 1,497,960
fakeHit size = 16 bytes
TotalAlloc delta: 138,004,760 (131.61 MB) for 1,497,960 appends
per-hit cost: 92.13 bytes
final cap: 1,734,656 (cap*hitSize = 27,754,496 bytes = 26.47 MB)
```

**单次 `scanInto` 在 10 MB / 0 sample 下的 ~150 MB alloc 中，~131 MB 来自这里**，其余 ~20 MB 来自 `requiredScanStarts` 内部的 `starts` 增长、sort 缓冲分配等周边路径。

### 20.1.4 "假手术"验证

通过将 Rule #094 在 benchmark 规则集中注释（`hyperscan_go_100_rules_benchmark_test.go:202`），跑同一份 `BenchmarkEngineScan/10MB_0sampleMB`：

| B/op | 150,714,948 | **4,480,392** | **×33 缩减** |

决定性证据：修改前 150 MB alloc 中**96.9% 来自 Rule #094 的 `'e'` / `'E'` single-byte required literal**。

## 20.2 问题定性

这不是 Hyperscan 层面的问题，而是 `scankit` 的 required literal 提取算法对"大小写字符类 + 无偏移上界"组合的退化。具体包含三个互相叠加的因素：

1. **字符类 `[eE]` 退化为两个独立 single-byte literal**：编译器无法找到唯一的多字节 prefix，只能把每个字节单独注册。
2. **`max=-1` 无偏移上界**：candidate 命中位置之前的任意起点都被认为是潜在 match 起点，确认程序需要从所有起点出发验证。
3. **reset 策略放大分配**：`if cap > 1<<20 { nil }` 在 huge-append 场景下导致每次扫描都从 cap=0 重新 grow 而非复用。

任何一条独立都不致命，三者叠加才会产生 150 MB 的极端数字。

## 20.3 修复方向（按优先级排序，不动代码）

### 20.3.1 P0：禁止 `[eE]` 这类字符类被单独提为 required literal

`internal/parser` 或 `internal/prefilter` 在提取 required literal 时，如果候选是大小写字符类（character class），应回退到以下两种策略之一：

- **策略 A：合并到上下文**。把 `[eE]` 与其前后必然存在的 token（如 Rule #094 里的 `[0-9]+(\.[0-9]+)?`）合并成一个多字节 literal，例如 `\.e`、`\.E`、`+e`、`+E`，再交给 `splitRequiredLiterals` / `newLiteralMatcherFinder` 处理。这样 candidate 命中密度从 `e 在英文文本中 ~15%` 降到 `\.e` / `+e` 等罕见组合的近 0。
- **策略 B：不下发到 requiredIndex**。如果字符类无法安全合并（例如 `e` 出现在表达式的第一个 token），就让这条规则直接走 backend 整块扫描（`backendOnly=true`），不进入 requiredIndex。

实现位置：`internal/prefilter/prefilter.go` 的 `graphPrefix` 与 `scanner.go` 的 `buildRequiredIndex`。

### 20.3.2 P1：`splitRequiredLiterals` 给 single-byte literal 加密度阈值

在 `scanner.go:512-522` 的 `splitRequiredLiterals` 之后、`newSingleByteFinder` 之前插入一道"输入密度预估"：

```text
candidateBytes := 扫描 N KB 样本，统计 single-byte literal 集合中每个字节的命中频率
if max(freq) > threshold (e.g. 5%):
    把这些 byte literal 标记为 high-density
    high-density 的 literal 不进入 newSingleByteFinder，转交 backend 整块扫描
```

为什么是 5%：英文文本里 `e` 约 12.7%、空格约 18%、`t` 约 9%，任何常见字母/空格都超过 5%。这种阈值可以让 Rule #094 的 `[eE]` 自动 fallthrough 到 backend 路径。

实现位置：`scanner.go` 的 `newRequiredFinder` 或外层 `newScanner`。

### 20.3.3 P2：`requiredHits` 的 reset 策略改进

`scanner.go:1387-1391`：

```go
if cap(ctx.requiredHits) > 1<<20 {
    ctx.requiredHits = nil
} else {
    ctx.requiredHits = ctx.requiredHits[:0]
}
```

问题：当 `requiredHits` 在某次扫描增长到 ~16 MB 后，下次扫描无论输入是否含 `'e'` 都会从 cap=0 重新 grow。改进方向：

- 保留一个"历史最大 cap"在 `scanContext` 上，reset 时把 `cap` 截断到 `max(cap, min(previous, 1<<20))`，避免每次从 0 开始。
- 或者改为 `cap > data_length × 32` 才释放（按输入大小动态调整）。

这条优化的收益取决于 P0/P1 是否生效；如果 P0 让 `[eE]` 不再进 requiredIndex，`requiredHits` 的高水位会自动降下来。

### 20.3.4 P3（可选）：Rule #094 改写为不依赖大小写字符类

直接修改 Rule #094 模式为：

```
[+-]?[0-9]+(\.[0-9]+)?(e|E)[+-]?[0-9]+
```

让编译器能识别出 `(e|E)` 仍然是字符类，但可能通过 NFagraph 的 normalize 步骤变成 alternation，进而能提取一个稳定的多字节 prefix（取决于 normalize 实现）。这是规则集层面的 workaround，**不推荐作为正式修复**，因为规则集是由 `vectorscan-source-map.md` 锁定的参考设计。

## 20.4 修复方案选型建议

| 方案 | 收益 | 风险 | 改动范围 |
|---|---|---|---|
| **P0 策略 A**（合并上下文） | 根本消除 single-byte literal | 需要正确处理字符类归一化 | parser / prefilter |
| **P0 策略 B**（不下发） | 简单、改动小 | 高密度场景下 backend 路径成本上升 | scanner.go:421-444 |
| **P1（密度阈值）** | 自适应、通用 | 阈值选取需要大量样本验证 | scanner.go:486-510 |
| P2（reset 策略） | 边际收益 | 不解决 root cause | scanner.go:1387-1391 |

推荐组合：**P0 策略 B + P1**。策略 B 把 Rule #094 这种已知问题规则直接 fallthrough；P1 给其他类似的字符类规则兜底。P2 视实际数据再决定。

## 20.5 验证方法

## 21.2 ctx reset 后的 cap 状态

扫描完成后从 pool 中取出 ctx，记录 reset 之后的 cap：

```
requiredHits   cap=570,880 entries  (8.71 MB raw)  ← reset 保留（cap < 1<<20）
requiredStarts cap=0                (0)            ← reset 释放（cap > 1<<20）
```

`ctx.directMatches` 的 reset 逻辑位于 scanner.go:1395-1417 的 defer 块中——**完全没有针对 `directMatches` 的释放策略**，所以 cap 跨扫描保留复用。

## 21.3 用户原假设的修正

先前排查中曾猜测："高密度下 matches slice 自身的扩容会成为新瓶颈"。**这个假设是错的**：

- `ctx.directMatches` cap=241,322（5.52 MB）跨扫描保留，warm 状态下每次分配 = 0
- cold 状态下首次分配 ~27 MB（grow from cap=0 to 241K），但这是单次成本
- **真正每次都从 cap=0 重新分配的是 `requiredStarts`**，因为 reset 策略在 cap > 1<<20（即 > 1M entries，约 8 MB raw）时释放

## 21.5 grow 累计因子

独立 grow 模拟（cap=0 → target N）：

| target entries | uint64 alloc | raw data | 因子 |
|---|---:|---:|---:|
| 570K | 25.26 MB | 4.6 MB | **5.5×** |
| 1M | 39.75 MB | 8.0 MB | **5.0×** |
| 1.5M | 62.41 MB | 12.0 MB | **5.2×** |
| 2M | 78.16 MB | 16.0 MB | **4.9×** |

Go slice geometric grow 产生稳定 **~5× 累计因子**（每次 grow ≈2×，加 size class 对齐）。这意味着：

- raw data N bytes → 累计 alloc ~5N bytes
- 229K matches × 24 bytes = 5.5 MB raw → cold 扫描累计 ~27 MB（仅首次，warm 后复用 0 alloc）

## 21.6 110 MB 精确归因

按 reset 策略推断每次扫描的 grow 起点：

| 路径 | 起点 cap | 终点 cap（推断） | raw 增量 | 单次 alloc 累计 |
|---|---:|---:|---:|---:|
| `requiredHits` | 0（cold）/ 570K（warm） | 570K | 8.7 MB | ~43 MB（cold）/ 0（warm，cap 够） |
| `requiredStarts` | **0（每次）** | ~2M-2.5M | 16-20 MB | **~80-100 MB** |
| `directMatches` | 0（cold）/ 241K（warm） | 241K | 5.5 MB | ~27 MB（cold only）/ 0（warm） |
| `appendGuardRunStarts` emitRun | 跟随 requiredStarts | 跟随 | 包含在 starts 里 | ~25 MB |

**`requiredStarts` 占稳态分配的主导**：每次扫描 cap 都从 0 grow 到约 2M entries（>1M entries 触发 reset 释放），累计 ~80-100 MB alloc。

## 21.7 三个独立修复点（按优先级）

### P1：`requiredStarts` 的 reset 阈值调整

**当前**（scanner.go:1389-1391）：

```go
if cap(ctx.requiredStarts) > 1<<20 {  // > 1M entries ≈ 8 MB raw
    ctx.requiredStarts = nil
} else {
    ctx.requiredStarts = ctx.requiredStarts[:0]
}
```

**问题**：10000 sample 下 requiredStarts 增长到约 2M entries（16 MB raw），超过阈值被释放。下次扫描又从 0 grow 累计 ~80-100 MB。

**修复方向**：

- 简单方案：提高阈值到 `1<<24`（>16M entries），让绝大多数 case 不触发释放
- 自适应方案：`cap > data_length × 8 / 8 = data_length` 才释放，按数据大小调整
- 激进方案：直接不释放，让 cap 自然增长到稳态

### P2：`directMatches` 加 reset 策略

**当前**（scanner.go:1395-1417）：无 `directMatches` 释放策略 → cold 扫描首次分配 ~27 MB grow 累计；warm 复用 0 alloc。

**问题**：在并发场景下每个 goroutine 冷启动一次，会累积大量内存峰值。

**修复方向**：跟 `requiredStarts` / `requiredHits` 一致加 reset 策略：

```go
if cap(ctx.directMatches) > 1<<18 {  // > 256K entries ≈ 6 MB
    ctx.directMatches = nil
} else {
    ctx.directMatches = ctx.directMatches[:0]
}
```

但 P2 是 cold-start 优化，对 warm 状态无影响。

### P3：`appendGuardRunStarts` 的 emitRun grow 优化

**当前**（scanner.go:2176-2181）：

```go
starts := emitter.starts
if cap(starts)-len(starts) < count {
    starts = slices.Grow(starts, count)
}
base := len(starts)
starts = starts[:base+count]
```

`emitRun` 把 guardRun 命中段展开为 starts，累计 ~25 MB alloc。修复方向是预先按段长度 `count` 一次性 grow 到合适大小，避免段内逐元素 grow 的累计因子。

## 21.8 修复效果预估

| 场景 | 当前 B/op | 修复 P1 后预估 | 修复 P1+P2+P3 后预估 |
|---|---:|---:|---:|
| 10MB_10000sample | 111 MB | **~30 MB** | **~10 MB** |

P1 单独就能省 80 MB（`requiredStarts` 占大头）。剩下 30 MB 主要是 cold 扫描首次 grow + 其他 helper。

## 21.9 与 §20.6 的关系

§20.6 提到"高密度段仍然受 `directMatches` grow 影响，这一部分仍待排查"。本章节实证结论：

- `directMatches` grow 在 warm 状态下分配 = 0（cap 保留复用）
- **真正每次都触发 grow 的是 `requiredStarts`**，而非 `directMatches`
- §20.6 的猜测方向部分正确（"高密度 grow"），但具体路径需要修正（从 `directMatches` 改为 `requiredStarts`）

2. **唯一仍有 alloc 的 case**：`BenchmarkEngineScan/10MB_10000sampleMB`（45 allocs/op，120 MB B/op）。这是 §21.6 中识别的 `requiredStarts` 反复 grow 问题，需要 §21.7 P1 修复。
3. **EngineMask vs GoRegexpReplace 稳定吞吐比**：在所有 case 上 EngineMask 比 GoRegexpReplace 快 50× ~ 400×。`AllPIITypes/HighMatch` 案例最极端：593 MB/s vs 7.43 MB/s（80×）。
4. **`PIIRedactionRules100/HighMatch/ScannerScanInto`**：246,612 ns/op，6,400 matches/op，**0 allocs**，654.76 MB/s。这是 `ScanInto` 在高密度下的真实稳态性能。

## 22.6 B/op 数字的稳定性说明

本章节的 `B/op` 列来自 `testing.Benchmark` 的内部 `MemStats` 测量，仍受 cold-start 摊销影响（每次跑测试 b.N 不同）。如果关注"绝对字节数"，B/op 可能小幅波动：

| Case | 第 1 次跑 B/op | 第 2 次跑 B/op | 偏差 |
|---|---:|---:|---:|
| EngineScan/10MB_0sample | 2,535,243 | 1,055,918 | 2.4× |
| EngineScan/10MB_10000sample | 120,205,918 | 116,267,324 | 1.03× |

**`allocs/op` 列稳定**（多次跑变化 ≤1 alloc），是真正可靠的基线指标。

后续对比应**优先看 `allocs/op`**：

- `EngineMask` / `ScannerScanInto` 应该保持 0 alloc
- `BenchmarkEngineScan/10MB_10000sampleMB` 应从 45.0 alloc 下降到接近 0（§21.7 P1 修复后）
